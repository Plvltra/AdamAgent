## 目标与分阶段交付

只读子 Agent 可以提出一个文件的一处替换。主 Agent 核对来源、展示差异并取得用户批准后，才通过原编辑流程应用。
候选存在不代表子任务成功、用户批准或文件已修改；子任务不能通过提案扩大权限。

## T11.1 数据与来源

| 数据 | 由谁提供 | 保存内容 |
| --- | --- | --- |
| ProposalOwner | 可信宿主 | 主会话、主轮次、子会话与派发 run_id；主任务收集时还须核对实际委派索引 |
| ProposalEdit | 模型提出 | read_call_id、old_text、new_text、reason；不接受模型指定路径、版本、所属会话或批准状态 |
| ReadEvidence | 真实 read_file 记录 | 子轮次内读取请求/调用 ID、工具返回的实际绝对路径、完整文件 SHA-256、可见行范围 |
| EditProposal | 提交服务生成 | 随机提案 ID、所属派发、提交来源、读取证据、补丁及纯编辑规划得到的目标版本 |

read_file 的路径由现有 PathPolicy 解析，随工具结果固定保存。
后来更改输入路径或源文件不能改变这份历史证据；缺少路径和可见正文的旧结果或通用预览不能作为新提案依据。
模型可提出错误修改，程序验证来源与执行条件，不验证修改的语义正确性。

## 提交顺序与失败边界

1. 取得执行器固定的当前轮次、请求和提交调用；只查本子会话、本轮指定的已完成 read_file。
2. 核对真实输出成功、行号连续、路径与版本有效，旧文本全部位于实际返回的可见行。
3. 重新按当前读取权限打开记录中的目标，核对完整原字节版本；逐行比较，拒绝行内被截断的文本。正常的分段读取允许提交。
4. 复用纯 plan_edit 检查全文件唯一匹配、确有变更、文件大小与编码换行约束，计算目标字节的 SHA-256；不写文件。
5. 核对尚在执行的真实 submit_proposal 及其参数，预检后在会话锁下保存 proposal_submitted。只有落盘成功才返回候选。

输入/来源/过期错误作为 ToolError；日志 IO 故障作为 StorageError 停止。取消不追加候选。
当前文件在步骤 3 后仍可能被其他进程修改，因此主任务应用必须再次授权并检查版本，不能信任曾经通过的检查。

每子轮最多 8 份提案；旧/新文本各最多 32 KiB UTF-8，理由最多 500 字符及 2000 字节，读取证据窗口最多 64 KiB。
提交参数中的 CRLF 规范为 LF；原文件 BOM、CRLF 等字节规则由原编辑规划保留。允许删除（新文本为空），不允许空旧文本、无变化及重复匹配。
证据窗口不补造末行换行；需要替换跨行文本时，应实际读到对应完整行。

## 持久化与恢复

proposal_submitted 追加到现有子会话 JSONL v4；回放重新核对所属子会话、轮次/请求/调用、真实读取及提交参数。
重复提案 ID、同调用重复提交、超额或同子轮改变派发身份均拒绝。
回放不重读当前源文件、不重算旧目标内容、不执行提案；主任务应用时再核对当前版本和候选目标哈希。

提案保存后、工具结果或子轮成功提交前退出，候选仍作为已发生的诊断事实保留。
原恢复机制结束遗留轮次；不会自动批准、应用、重发或将候选视为可交付的成功子任务结果。
显式 load_proposals 可读这些诊断记录；T11.2 的主任务入口另外验证实际委派和成功子轮，不因候选存在就允许应用。

## T11.2 工具接入与审核应用

| 工具 | 所在任务 | 输入与结果 |
| --- | --- | --- |
| submit_proposal | 辅助子 Agent | 读取调用 ID、旧/新文本和理由；返回已保存候选 ID，不修改文件 |
| collect_proposals | 主 Agent | agent_id、run_id、index、offset；每页保留提案 ID、实际路径和分页位置，正文是候选 JSON 的字符片段 |
| apply_proposal | 主 Agent | agent_id、run_id、proposal_id、path；重新核对后展示原编辑 diff，取得批准才应用 |

审查者不注册上述工具，辅助子任务只注册 submit_proposal，不能应用、申请批准或再次委派。
先通过 wait_agents 收集子任务结果，再按 index、next_index 选择候选，跟随 next_offset 读完正文。
每页按实际 JSON 字符长度满足工具结果上限；身份字段放不下时明确失败，不退化成丢失 ID 的预览。
分页读取仍计入原工具数、请求数和上下文预算，不因候选较长无限扩张额度。

SubagentManager.candidates 每次核对所属主会话、辅助角色、实际派发、完整成功子轮及成功提交输出。
运行中、失败、中断或没有完整成功历史的子任务不能提供可应用候选。
同主会话的旧成功派发允许显式查询，不把上一轮失败的候选自动升级为可用；跨会话 ID 拒绝。

apply_proposal 的 path 是复制自收集结果的审计确认值。参数校验要求它与真实候选完全一致，
随后原目录规则与 Hook 才看到该路径。实际写入的路径、补丁和版本均来自子日志；模型不能替换补丁或版本。
这样现有 Hook v1 可以检查真实目标，无需引入隐式参数改写。两个仓库 Hook 示例已覆盖 apply_proposal；
用户自己的检查器若按工具名称分支，也需将新入口纳入相应策略，程序不自动修改用户脚本。

应用按“核对来源 → 检查是否重复 → 当前写入权限/版本及目标哈希 → 原批准和写入流程”执行。
ProposalReview 只协调；EditTools.execute_plan 同时服务 replace_text 与提案应用，
保留 diff、人工拒绝、写入前再检查、检查点、编辑日志及结果未知策略。
共享 FILE_EDIT_TOOLS 让编辑额度、日志来源、计划证据、执行报告和审查期间的修改限制同时识别两个入口；
Conversation 和 CLI 不增加提案名称分支。

主会话 edit_planned 附带完整 proposal，校验实际 apply_proposal 参数、所属主会话、原主轮次及计划版本。
edit_finished 不能改写候选；普通 replace_text 不能冒认提案来源。
应用状态只取原编辑事件：applied 或 unknown 的候选均不能重做，撤销之后也不重新开放旧候选。
子会话仍保存提交来源；收集不另建重复候选数据库，普通工具结果记录保存模型实际看到的页面。
重启不自动收集或应用。两个真实子任务与进程故障组合仍在 T11.3 验收。
