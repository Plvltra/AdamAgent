## 1. 项目目标与约束

做一个自己愿意使用的小型编程 Agent，从终端聊天逐步发展到会话管理、上下文管理、文件修改和命令执行。主要目标是练习完整软件的设计、实现、测试、排错和交付，而不是追求代码规模或复刻 DeepSeek Harness。

- 开发基础：有 C++/Python 和现有系统局部开发经验；模块划分、Git、调试已有基础；HTTP API、数据库和部署需要补齐；异步与并发需要系统练习。
- 时间：每周十几个小时，第一轮规划 6～8 周。
- 首次交付：争取两个晚上、约 4～6 小时完成终端聊天及会话保存恢复。
- 模型：DeepSeek API，每月几十元预算；实际消耗通过日志校准，不预先承诺调用次数。
- 分工：开发者设计框架，自己与 AI 各承担部分代码；AI 负责 Agent 知识讲解、设计审查、边界场景和排错协助。
- 首轮使用 Python。C++ 仅在后续有可测量的本地计算瓶颈，或明确的跨语言专项学习目标时引入。

## 3. 各版本范围与验收

### V0：终端聊天

**用户成果**：在终端进行内存多轮聊天；持久化与恢复在 V1 实现。

范围：
- 使用一个远程模型服务，同步、非流式请求。
- V0 提供新建和退出命令；列出、恢复会话在 V1 实现。
- V0 仅保存内存历史；V1 直接使用 SQLite，不经历 JSON 文件迁移。
- V0 成功后才保存完整轮次到内存；待完成请求记录在 V1.3 实现。
- API 密钥从本地模型配置或环境变量读取，不进入 Git、聊天记录或日志。
- V1 使用 SQLite 事务保证完整轮次原子保存。

验收：
- [ ] 连续多轮聊天能引用前文。
- [ ] 新建两个会话，分别退出、恢复，内容不串话。
- [ ] 重启程序后能列出并恢复历史会话。
- [ ] API 错误或超时有清楚提示，不伪造成功回答。
- [ ] 保存失败可见，不静默宣称已保存。
- [ ] 能说明一次请求从输入到保存的完整数据流。

建议安排：第一个晚上打通请求和多轮聊天；第二个晚上完成会话命令、保存恢复和失败提示。暂不加入工具、数据库、插件系统和图形界面。

### V1：可靠的会话

**用户成果**：能够判断某轮对话是完成、失败还是被中断，并查到排错信息。

范围：
- 将存储迁移到 SQLite，使用标准库 sqlite3 和基本 SQL。
- 设计会话、消息和请求/轮次状态，记录稳定 ID。
- 记录状态、耗时、模型和可用的 token 用量，日志避免泄露密钥。
- V0 没有持久化文件，不安排 JSON 导入；后续表结构升级须保留现有 SQLite 数据。
- 重启时识别未完成操作，不自动把它们当成功，也不静默重发。
- 引入假模型，让失败和超时测试不依赖实际付费请求。

验收：
- [ ] 两个会话的数据隔离可通过测试验证。
- [ ] 请求等待中退出，重启后能识别未完成轮次。
- [ ] 后续数据库结构升级保留现有会话内容和消息顺序。
- [ ] 持久化相关错误不会留下被误认成成功的状态。
- [ ] 能通过日志定位一次请求失败，而无需猜测执行到哪一步。

### V2：只读 Agent

**用户成果**：提出一个代码或文档问题，模型自行决定读取和搜索哪些文件，再组织回答。

范围：
- 工具：列目录、读取文件、搜索文本。
- 实现“调用模型 → 工具请求 → 执行 → 回传结果 → 再调用模型”的循环。
- 工具参数验证、调用 ID 与结果关联、错误结果反馈。
- 工作目录范围控制、文件读取和工具输出大小上限。
- 单任务步数上限；工具先串行执行。

验收：
- [ ] 一次任务能经过至少两步工具调用后回答。
- [ ] 文件不存在、参数不合法、未知工具均有明确结果。
- [ ] 工具请求和结果关联正确，不将工具结果伪装成用户输入。
- [ ] 达到步数上限时停止并说明原因。
- [ ] 假模型可以确定性复现完整工具调用循环。

### V3：上下文管理

**用户成果**：可以检查某次请求实际发送了什么，并控制长对话的上下文成本。

范围：
- 分离完整持久化历史与本次请求的模型上下文。
- 增加上下文预算，保留输出余量；区分估算与服务端实际用量。
- 工具输出截断，按完整消息组选择历史。
- 手动触发旧历史摘要，保留原始记录并标明摘要覆盖范围。
- 提供请求上下文查看或调试导出功能。

验收：
- [ ] 能查看一次请求实际发送的消息。
- [ ] 长工具输出不会无限扩大后续上下文。
- [ ] 裁剪不拆散工具调用与对应结果。
- [ ] 摘要或裁剪不覆盖、删除原始历史。
- [ ] 用固定对话样例验证关键约束在裁剪后仍保留；失败样例可复现。

### V4：小型编程助手

**用户成果**：在练习仓库中定位小问题，展示修改，确认后写入并执行测试。

范围：
- 文件修改预览与 diff，确认后应用。
- 写入前检查文件是否相对读取时发生变化，避免覆盖期间的人为修改。
- 命令执行工具：明确工作目录、参数、退出码、标准输出和错误输出。
- 命令超时、输出上限和执行记录。
- 写入与命令执行的确认策略；明确路径边界。
- 对副作用操作保留状态；结果不明确时不盲目自动重试。

验收：
- [ ] 在练习仓库完成一次“定位问题 → 展示 diff → 修改 → 运行测试”。
- [ ] 拒绝修改或命令时，不执行对应动作。
- [ ] 文件被外部修改后，旧修改计划不会直接覆盖它。
- [ ] 超时或非零退出码能准确反馈给用户和模型。
- [ ] 任务失败时能报告已执行的修改和命令。

边界：应用层确认、路径检查不是操作系统沙箱。此阶段先针对受控练习仓库，不宣称能安全运行任意不可信命令。

### V5：日常使用与首轮收尾

**用户成果**：能看到逐步输出、停止任务，安装后稳定使用并方便排错。

范围：
- 流式输出，区分完整回答与中断的部分输出。
- 取消传播到模型等待与运行任务；对子进程清理定义明确行为。
- 分类重试、次数上限和退避；只对适合重试的操作启用。
- 整理配置、启动方式、依赖锁定和使用文档。
- 固定回归样例与少量真实模型验收。

验收：
- [ ] 可以取消等待或执行中的任务，状态正确收尾。
- [ ] 中断后会话可以继续，不将残缺协议消息直接作为正常历史发送。
- [ ] 无效参数或鉴权错误不会无限重试。
- [ ] 副作用结果不确定时，不自动重复执行。
- [ ] 在干净环境按文档可以安装启动。
- [ ] 关键回归验证不依赖实际模型输出的随机性。

## 5. 技术选型与架构边界

| 领域 | 首选 | 引入阶段 |
| --- | --- | --- |
| 语言 | Python，固定项目版本 | V0 |
| 项目管理 | uv、pyproject.toml、依赖锁文件 | V0 |
| HTTP | HTTPX，同步起步 | V0 |
| 模型服务 | DeepSeek，模型名与连接参数可配置 | V0 |
| 界面 | input/print 与少量命令 | V0 |
| 数据类型 | 类型标注、dataclass | 随数据复杂度逐步加入 |
| 存储 | 内存 → SQLite（标准库 sqlite3） | V0 → V1 |
| 验证 | pytest、假模型、故障注入 | V1 起系统化，V0 保留基本验证 |
| 并发 | asyncio | 取消及并发需求出现时 |
| Web 服务 | FastAPI；简单页面起步 | V7 |

职责演进方向：

```text
CLI / Web
    ↓
对话执行流程
    ├── 会话存储：记录发生过什么
    ├── 上下文构建：决定本次模型能看到什么
    ├── 模型接口：发送请求并解释响应
    └── 工具执行：验证参数、执行、返回结果
```

V0 使用少量模块和普通函数即可。不要首日搭建通用插件框架；工具执行与独立上下文模块在相应版本引入。重点验证两个边界：换成假模型后能测试流程；换成 Web 后能复用核心。

## 6. 每版完成标准与开发节奏

每版除了功能验收，还应：
1. 画出一次完整数据流，解释状态在哪里变化。
2. 人为构造一个失败场景，通过日志定位，并留下有价值的回归验证。
3. 解释一项设计取舍，例如串行执行、重启不自动重试、历史与上下文分离。
4. 记录尚未解决的限制，再进入下一版。

开发者先设计数据结构、接口与主流程；AI 协助知识讲解、边界分析、重复代码和审查。涉及状态变化的 AI 代码，必须能解释其分支和失败行为。

成本控制：日常回归优先假模型；阶段验收使用真实 API；记录用量，设置任务步数和输出上限。月预算依实际消耗调整。
