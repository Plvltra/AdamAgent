# Adam：版本规划与学习路线

更新日期：2026-10-29

项目目录：`G:\Myself\Adam`

## 1. 目标与规划规则

做一个可用的小型编程 Agent，练习完整软件的设计、实现、测试、排错与交付。使用熟悉的 Python，C++ 等出现可测性能瓶颈或专项学习需要后再引入；每周十几个小时，DeepSeek API 月预算几十元。

开发者设计核心并理解实现，AI 提供概念、设计审查和排错帮助。按验收推进，不以代码规模或“AI 已写完”为完成标准。

[agent-practice-todo.md](agent-practice-todo.md) 是详细任务与完成状态的主记录；本文件维护版本概览与依赖。新增任务直接归入对应阶段，失效任务删除，不再堆叠“优先于正文”的历史补丁。

## 4. 第二轮扩展版本

以下为候选顺序，首轮完成后再细化工时与技术选择。V6 前先完成职责包整理，相关文件与依赖边界见 [系统架构](architecture.md)；目录整理不代表多会话并发已实现。

| 版本 | 交付内容 | 重点验收 | 学习价值 |
| --- | --- | --- | --- |
| V6 子 Agent 协作 | 一个终端一个主会话，主 Agent 委派、追问与汇总；见 [分步规划](subagents.md) | 子任务真正并行、共享额度、单独取消、重启不重发 | 资源所有权、并发准入、取消传播 |
| V7 本地 Web | 会话列表、消息流、工具状态、停止按钮 | CLI 与 Web 复用核心；刷新能恢复状态；不重复提交任务 | FastAPI、前后端协议、状态同步 |
| V8 部署交付 | 独立环境运行、配置、重启、日志、备份 | 可安装、重启恢复、备份还原；远程开放前具备访问控制 | 服务部署与运维 |
| V9 扩展机制 | 新工具或第二个模型适配器 | 无须修改主循环即可扩展；兼容性行为可验证 | 接口、依赖方向、配置 |
| V10 扩展评估 | 建立固定任务基线（或复用后续补做的 V2.3）并长期对比 | 策略变化有可重复对比，区分模型失败与程序故障 | 评估设计、成本与质量取舍 |
| 可选性能专项 | Profiling 与热点优化 | 有基准、正确性对照、优化前后数据 | 性能分析，按需引入 C++ |

多 Agent、向量检索、插件热加载和复杂前端框架不预先加入第一轮。出现具体需求后再决定。

## 5. 技术选型与架构边界

| 领域 | 首选 | 引入阶段 |
| --- | --- | --- |
| 语言 | Python，固定项目版本 | V0 |
| 项目管理 | uv、pyproject.toml、依赖锁文件 | V0 |
| HTTP | HTTPX，同步起步 | V0 |
| 模型服务 | DeepSeek，模型名与连接参数可配置 | V0 |
| 界面 | input/print 与少量命令 | V0 |
| 数据类型 | 类型标注、dataclass | 随数据复杂度逐步加入 |
| 存储 | 内存 → JSONL v4（标准库 JSON + 文件锁） | V0 → V1 |
| 验证 | pytest、假模型、故障注入 | V1 起系统化，V0 保留基本验证 |
| 可取消 IO | asyncio 驱动 HTTPX 异步传输，同步应用接口 | V5.2；尚无并发多 Agent |
| Web 服务 | FastAPI；简单页面起步 | V7 |

已完成配套错误边界整理：公开业务失败遵循 AgentError，CLI 只依赖统一展示契约；预算停止、模型失败和未保存回答分别表达。存储 IO 故障在本模块转换，程序错误继续传播。V1.3.2 已进一步接入持久化状态、原因和耗时；组件组装及会话查询已分别移至 bootstrap 与 AgentApplication，当前关系见 [系统架构](architecture.md)。

职责演进方向：

```text
CLI / Web
    ↓
对话执行流程
    ├── 会话存储：记录发生过什么
    ├── 上下文构建：决定本次模型能看到什么
    ├── 模型接口：发送请求并解释响应
    └── 工具执行：验证参数、执行、返回结果
```

V0 使用少量模块和普通函数即可。不要首日搭建通用插件框架；工具执行与独立上下文模块在相应版本引入。重点验证两个边界：换成假模型后能测试流程；换成 Web 后能复用核心。

## 6. 每版完成标准与开发节奏

每版除了功能验收，还应：
1. 画出一次完整数据流，解释状态在哪里变化。
2. 人为构造一个失败场景，通过日志定位，并留下有价值的回归验证。
3. 解释一项设计取舍，例如串行执行、重启不自动重试、历史与上下文分离。
4. 记录尚未解决的限制，再进入下一版。

开发者先设计数据结构、接口与主流程；AI 协助知识讲解、边界分析、重复代码和审查。涉及状态变化的 AI 代码，必须能解释其分支和失败行为。

业务功能点测试集中在 `tests/features/`，入口见 [功能测试导航](../tests/features/README.md)；其余模块测试继续覆盖配置、存储和协议等基础校验。业务测试随功能变更扩展，V1.3 的状态、诊断和恢复均已验收，V2.3 暂跳过；V3 已覆盖预览、整轮选择、手动/自动摘要及缩减的成功、失败和预算边界。V4 增补文件编辑、真实强杀恢复、有限修正及执行事实报告，V5 覆盖流式、取消、有限重试、失败继续与干净环境交付；提交钩子执行全量 pytest、Ruff 和 Pyright。

成本控制：日常回归优先假模型；阶段验收使用真实 API；记录用量，设置任务步数和输出上限。月预算依实际消耗调整。假 HTTP 不代替真实模型效果评估。
