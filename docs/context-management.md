# V3.1：上下文构造、预览与输入预算

更新日期：2026-10-28。V3.1 已实现；下一步为 V3.2 完整轮次选择。架构见 [系统架构](architecture.md)，完成状态见 [练手 TODO](agent-practice-todo.md)。

## 这一版解决什么问题

JSONL 记录过去发生的事，模型每次只看到这次请求发送的内容。V3.1 先把“构造本次输入”从对话循环中提取出来，让你能查看组成，并在发送前发现输入过大。当前仍使用全部成功历史，尚未裁剪或生成摘要。

| 数据 | 包含什么 | 用途 |
| --- | --- | --- |
| 会话 JSONL | 成功消息，以及失败、请求、工具和恢复事件 | 保存原始记录与诊断依据 |
| 基础上下文预览 | 当前会话系统提示、成功历史、当前工具说明 | 查看下一次请求的已有基础，不含尚未输入的新问题 |
| 实际请求上下文 | 基础内容加本轮用户输入、已经产生的工具调用及结果 | 每次模型请求前重新构造和检查 |

失败输入保留在诊断记录中，不进入下一轮的成功历史。系统提示使用当前会话创建时保存的值；模型使用本次配置或 `/model` 的当前选择。

## 怎么查看

启动 Adam 后输入：

```text
/context
/context full
```

`/context` 显示模型、消息/工具数量、系统/历史/本轮/工具说明的估算、输入限额与剩余量、单独的输出预留。`/context full` 在此基础上展开完整 `messages` 与 `tools` JSON。

它们不请求模型、不计费、不创建会话、不写入历史；空会话也可以看，超预算也可以看。程序启动时既有的模型目录查询仍可能联网，和这两个命令无关。

预览的“本轮”估算为 0，因为此时还没有下一条输入。输入新问题后，实际发送会重新检查。它不是最近一次请求快照；查看完整预览也不会生成历史请求归档。

## 配置与三个数字

在实际使用的 `config.toml` 中加入；省略时采用相同默认值：

```toml
[context]
max_input_tokens = 32768
safety_margin_tokens = 2048

[agent]
max_output_tokens = 4096
```

已有 `[agent]` 时在原节里修改，不重复声明 TOML 节。其他累计用量和次数限制继续生效。

| 配置 | 含义 |
| --- | --- |
| `context.max_input_tokens` | 应用愿意发送的单次输入上限，含安全余量 |
| `context.safety_margin_tokens` | 给估算误差留的空间，必须小于输入上限；允许 0 |
| `agent.max_output_tokens` | 请求的输出上限，位于输入预算之外，沿用已有配置 |
| `agent.max_session_tokens` | 会话累计消费上限，由服务端 usage 记账；不参与上下文大小估算 |

发送条件：

```text
估算输入 = 系统提示 + 成功历史 + 当前轮次 + 完整工具说明
估算输入 + 安全余量 <= max_input_tokens
```

默认情况下，估算输入最多 30,720 token；再加 2,048 余量占满 32,768 的输入预算。输出另预留 4,096，因此输入上限加输出预留为 36,864。这里没有自动查询模型真实窗口；配置应适配所选模型，切换模型也不会自动修改它。

输出不能在输入检查时再扣一次，否则同一份预留会重复计算。`/usage` 统计多次请求累积的实际消费，包含重复发送的历史和输出；`/context` 只估算下一次输入的基础，两个数不应相等。

## 估算怎样得到

每条消息按紧凑 JSON 序列化，取 UTF-8 字节数除以 3 向上取整，再加 8 个结构开销。系统、成功历史和本轮分别求和；完整工具 Schema 列表另外计算一次。没有内容的部分记 0。

这是便于调试、无需额外依赖的启发式估算。中文、工具描述、参数 Schema、调用参数和服务商推理字段都纳入长度；不同模型的实际 tokenizer 和服务端协议开销可能不同，安全余量也不能保证请求一定不超模型窗口。账单和会话消费始终以服务端 usage 为准，不拿估算写入消费记录。

## 超限时会发生什么

每次模型请求前检查，执行顺序为：

1. 读取成功历史，构造消息和工具说明。
2. 检查既有累计消费和当前输入预算。
3. 检查通过才写 `request_started` 并调用模型。
4. 模型要求工具时执行并记录；工具结果加入本轮后，回到构造和检查。

例如第一次请求要求读取文件，文件结果较大，第二次请求输入超限：

- 第一条请求仍是成功，其实际用量保留。
- 工具开始、结果记录仍保留，便于解释为什么输入增长。
- 第二条请求没有发起，不生成假的请求记录或未知用量。
- 整轮记录 `failed / context_input_limit`；这条失败工具链不提交为成功历史。
- 终端说明超出多少，以及缩短输入、新建会话或调整配置等处理方式；不自动裁剪或重试。

请求前单条用户输入、旧历史或工具说明本身就过大时也采用这个规则。日志结构继续使用 v4；新增的是稳定原因码，没有新快照事件。

## 验收依据

业务场景在 [test_context_preview.py](../tests/features/test_context_preview.py)，经过实际 CLI/Conversation、临时 JSONL 和真实文件工具，只有 HTTP 模型响应是模拟的。覆盖只读命令、工具协议保真、切换与恢复、三种输入来源超限、工具结果增长，以及主配置到 CLI 的实际传递。

基础场景在 [test_context.py](../tests/test_context.py) 和 [test_config.py](../tests/test_config.py)，检查副本与原历史分离、中文和 Schema 长度、恰好达到上限与超出 1 token、非法值和默认配置。

2026-10-28：新增 19 个用例，全量 **226 passed in 36.77s**；Ruff 格式、lint 与 Pyright 通过。自动化验证本地工程行为，不声称验证所有模型的精确 token 数。

个人练习：先查看空会话预览，聊一轮后再查看全文，指出新增的 user/assistant 消息；随后比较 `/usage` 和 `/context`，解释为何累计消费与下一次输入大小不同。
