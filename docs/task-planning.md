# E3 显式任务计划

更新：2026-10-29。主任务以 [练手 TODO](agent-practice-todo.md) 的 E3 为准。
E3.1～E3.4 已完成离线验收：计划记录、模型工具、证据校验、终端交互与两文件业务对照。

## 已确认范围

- 多步骤任务由模型按需调用计划工具；简单问答跳过，用户可以要求先列计划。
- 每个用户轮次一份计划；历史留在会话 JSONL，下一轮可参考但不继承待办状态。重启只读恢复，不自动重跑。
- 完成步骤必须关联本轮真实工具结果。程序验证来源及执行状态，不声称能判断语义证据充分性。
- 建立或更新时显示简短清单，/plan 查询当前会话最近计划；第一版仅主 Agent 维护计划。
- 有未闭合步骤却准备最终回答时最多提醒一次，仍使用现有请求额度；再次遗漏则明确显示未完成，保留回答。
- 默认最多 8 步、同时 1 步进行中、每轮重规划 3 次，数量可配置。增删、改写、重排或重开已结束步骤计重规划；普通进度更新不计，旧版本和原因保留。
- E3.1～E3.4 每步验证并单独提交，作者 Plvltra。主线按 E1 → E2.1～E2.5 → E3.1～E3.4 排列，保留两个功能的各阶段记录。

## E3.4 两文件对照验收

场景：同一临时工作目录中的 a.py、b.py 从 VALUE = 1 修改为 VALUE = 2，分别经过 read_file 和用户批准的 replace_text，最后实际运行 Python 子进程核对两个文件。两组只改变计划开关，使用相同任务、文件初值、工作目录和审批行为；会话数据分别保存，关闭应用后重新打开验证结果。

| 项目 | 普通工具循环 | 显式计划 |
| --- | --- | --- |
| 两个文件修改及检查 | 通过 | 通过 |
| 模型请求 | 4 | 5 |
| 实际工作工具 | 5：读取 2、编辑 2、命令 1 | 同左 |
| 计划更新工具 | 0 | 4 |
| 编辑/命令审批 | 3 | 3 |
| 计划版本及完成依据 | 无 | 4 版，三个步骤分别引用读取、编辑和命令结果 |
| 本次累计输入估算 | 8,948 token | 17,341 token |

输入估算来自 request_started.context，包含重复上下文与工具说明，临时路径变化会使数字略变；不是服务商计费用量。测试只要求方向，不锁定估算数字。该脚本中显式计划多 1 次请求、4 次工具调用；它让状态和依据可查，也增加开销，不能推出真实模型成功率更高。远端使用 MockTransport，本地文件、审批入口、命令子进程与 JSONL 都实际执行，不消耗 API 额度。

[业务对照测试](../tests/features/test_task_plan_acceptance.py) 的 4 个场景已通过：两文件对照、子结果成功/失败两种证据边界、简单问答不建计划。子模型未注册 update_plan，即使伪造调用也返回未知工具；主 Agent 可以引用 wait_agents 的成功结果，子任务失败则拒绝 completed。已知用量的子响应协议失败用于隔离证据校验，避免与共享未知消费保护混为一谈。

复现离线对照：

~~~powershell
.\.venv\Scripts\python.exe -m pytest -q -s tests/features/test_task_plan_acceptance.py
~~~

手工体验可在测试副本中输入：“先列计划，把 a.py 和 b.py 的 VALUE 从 1 改为 2，再运行命令核对；完成时说明依据。”模型选择建立计划后，终端显示进度，编辑与命令仍需批准；/plan 可查看最近结果。真实模型是否按需规划及所需成本仍需用户另行体验。

E2/E3 集成：E2 原工作树为 G:/Agent/adam-e2，已按阶段顺序接入主线；原 main 留有备份。bootstrap 同时注册 search_documents 和 update_plan，配置保留两组字段，架构图与 TODO 保留双方内容。新增一项业务验收：真实检索 → 标记计划完成并引用工具 ID → 重启读取证据；该文件现在共 5 个场景通过，合并后全量收集 579 项。远端仍使用假 HTTP，不把流程验收视为真实模型效果证明。

## E3.3 展示与收尾

建立或更新成功后显示清单、状态、版本及依据；工具结果先落盘再通知界面，展示异常向上传播并停止后续执行。/plan 只读当前会话最近计划，不创建会话、不请求模型，重启后仍可查看。步骤状态与轮次状态分开：回答已保存不表示所有步骤完成；失败或中断也不改写原步骤为成功。

有 pending/in_progress 步骤时暂存流式正文。模型提前给最终回答且仍有请求额度时，丢弃这次候选回答并提醒一次；后续若仍未闭合或额度不够，保留最终回答并打印“计划未完成”。提醒属于程序固定指令，不把模型步骤文本提升为系统指令；结束或切换会话后不残留提醒。工具、模型请求及 token 仍受原有额度约束。

工具失败后可调整计划并说明原因，超限更新被拒绝且保留原版本。failed/cancelled 必须带原因，表示步骤已明确结束，不冒充完成。跨轮不继承待办；用户可在下一轮明确要求模型根据旧计划继续。

验收：[计划交互](../tests/features/test_task_plan_interaction.py) 覆盖一次提醒、无额外请求额度、失败后有限调整、SSE 提前回答隐藏、只读查询与重启、展示失败后日志保留。与模型计划、错误反馈回归合计 25 项通过；提交钩子另执行全量检查。

## E3.2 模型工具与证据

主应用注册 update_plan，子 Agent 不注册。PlanningService 绑定程序提供的轮次/请求/工具来源，模型只提交步骤和原因，不能指定来源。before_call 同时给委派与计划服务提供关联，保留 V6 行为。

[planning] 配置 enabled=true、max_steps=8、max_replans=3；禁用时不向模型注册工具，不妨碍读取已有计划。首次建立把限制写入版本记录；后续状态更新不增加重规划次数。

session/plan_evidence.py 在追加和重放时校验：证据属于本轮且工具已结束，不能引用 update_plan 自身；completed 要求实际成功。run_command 另查执行记录的 completed 与 exit_code=0，replace_text 要求 applied，wait_agents 要求返回成员均已完成。其他工具依据实际回传结果，不把 ok=true 的失败状态当成功。语义证据是否充分仍由模型负责。

模型参数、版本及证据不合法时返回工具错误，保留上版计划；保存失败仍是 StorageError，停止后续工具与模型请求，不改成普通参数错误。真实来源先预检、落盘再复核。

验收：[模型计划](../tests/features/test_task_planning.py) 覆盖伪造、自引用、跨轮、失败读取证据，命令 0/非零退出码及保存失败；[配置](../tests/test_planning_config.py) 覆盖构造及 TOML 入口。

## E3.1 记录与恢复

contracts/planning.py 定义不可变步骤、完整快照及查询报告；session/plan_log.py 校验版本和重规划次数。SessionLog 校验更新所属轮次、请求和正在执行的 update_plan；SessionStore 复用原追加、文件锁与 fsync 回滚。

plan_updated 包含 turn_id、request_id、tool_call_id、version、steps、reason、replan_count、max_steps、max_replans。步骤包含稳定 step_id、content、status、evidence、reason。状态为 pending、in_progress、completed、failed、cancelled；失败和取消必须有原因，完成必须带证据引用。E3.2 已补引用的真实结果校验。

旧 v4 会话没有 plan_updated 仍可读；含新事件的日志不保证被旧程序读取。计划记录不自动加入成功消息历史。PlanReport 单独携带轮次终态；轮次被中断时保留原步骤，不伪造完成。新会话不会带入旧计划。

验收：[计划存储](../tests/features/test_task_plan_storage.py) 覆盖重启、版本、隔离、非法状态/关联、重规划上限和实际 fsync 失败。
