## 主线 V1：从内存到可靠会话（10～14 小时）

书中关联：2.2.1～2.2.4、3.1.2。目标：创建两个会话，关闭程序后恢复其中一个继续聊，内容不串话。工程前置：SQL、事务、状态与错误处理。SQLite 是本项目的教学选择，不是书中指定的唯一方案。

### V1.1 独立存储模块（先做，约两个晚上）

- [x] 实现 `sessions`、`messages` 的字段结构：会话 ID、消息所属会话、角色、内容、顺序；注明哪些字段必填。
- [x] 明确系统提示词和当前模型属于哪里，恢复时使用哪份值；不要混同“当前模型”与“历史消息实际由谁生成”。
- [x] 用 `sqlite3` 建库建表，先不引入 ORM。
- [x] 实现创建会话、列出会话、读取有序消息、保存成功轮次四个接口，签名由自己设计。
- [x] 所有 SQL 值使用参数绑定；明确连接由谁创建和关闭。
- [x] 把一轮用户消息和助手回答放进同一事务，写入失败整体回滚。
- [x] 以临时数据库写测试：关连接后重开仍能读取；两个会话隔离；中途失败不留下半轮消息。

验收演示：不调用 LLM，只通过存储接口完成“创建 A/B → 写入不同内容 → 关闭 → 重开 → 分别读取”。

自查：为什么不能依赖查询的默认顺序？没有 `commit` 会怎样？数据库主键和消息顺序是否必须是同一概念？

### V1.2 接入终端会话

- [x] 将会话存储接入现有聊天循环；保留原来的失败轮次不进入有效模型历史的行为。
- [x] 新建命令与 `/new` 语义对齐，添加会话列表和按 ID 恢复命令。
- [x] 恢复历史及会话保存的系统提示词，显示当前会话标识；模型使用当前配置或本次 `/model` 选择，不恢复历史模型。
- [x] 数据库忙、路径不可写、会话不存在时，显示可理解错误，不伪装保存成功。
- [x] 本地数据库文件不提交到 Git。

验收演示：A 记住一个代号，B 记住另一个；重启恢复 A，只能使用 A 的历史。

### V1.3 未完成轮次与请求记录

- [ ] 在设计中加入轮次/请求标识和进行中、成功、失败、中断状态。
- [ ] 用户输入先记录为待完成；成功后提交有效对话。失败记录可查询，但不直接作为正常历史发给模型。
- [ ] 请求日志记录模型、耗时、可用的 token 用量与错误类别，不记录密钥。

验收：用户能分辨“模型失败”“程序中断”“回答成功但保存失败”。这里是从 V0 简化规则到可恢复状态的明确演进。

## 主线 V2：只读工具与 Agent 循环（12～16 小时）

书中关联：1.1.5、2.2.3、4.2.2。目标：让模型自行选择文件工具，依据结果回答，而非程序预先写死读哪个文件。

### V2.1 先脱离模型实现工具

- [ ] 实现 `list_directory`、`read_file`、`search_text`，先用普通 Python 调用验证。
- [ ] 为每个工具定义名称、用途、参数类型、成功结果和错误结果。
- [ ] 解析真实路径并检查工作目录边界；考虑 `..`、绝对路径及链接逃逸。
- [ ] 限制单次文件大小、输出长度和搜索结果数；截断必须明确标记。
- [ ] 测试文件不存在、参数错误、越界、超大输出，保证错误可定位。

### V2.2 接通模型选择与结果反馈

- [ ] 扩展模型响应类型：文本回答或工具调用，不能继续只返回 `str`。
- [ ] 将工具说明发送给模型；按照实现时所用服务的工具协议构造消息。
- [ ] 完整保存模型工具请求，执行工具并以对应 `tool_call_id` 回传结果。
- [ ] 同一步请求多个工具时，先串行处理并为每个请求返回结果。
- [ ] 工具执行完再次调用模型；模型给最终回答、到达限制或用户取消时结束。
- [ ] 设置任务最大步数、工具输出上限和明确的停止原因。
- [ ] 用假模型脚本覆盖“先搜索 → 再读取 → 最终回答”“未知工具”“重复调用直到上限”。

验收演示：问“Adam 的模型配置在哪里读取，失败时怎么处理？”，由它搜索并读取代码，再给出带路径依据的回答。

自查：工具结果为什么不能当作用户消息？模型决定动作与程序批准执行有什么区别？保存可观察的工具轨迹即可，不依赖模型暴露内部思考过程。

- [ ] 失败时沿轨迹找首个导致偏离的步骤，不能仅把最后报错当作根因。

### E1 跨会话记忆（6～10 小时）

### E2 本地文档 RAG（10～16 小时）

书中关联：3.2.1 文档分块、3.2.3 稀疏检索、3.3.2 文件系统组织、3.3.4 智能体化 RAG。前置：V2、V3 和固定评估集。

- [ ] 选一个小文档集，先建立关键词搜索基线。
- [ ] 实现文档分块、来源路径、位置标记、文件更新后的索引刷新。
- [ ] 再选用一种 embedding 检索方式，比较召回效果；初版无需独立向量数据库服务。
- [ ] 回答中给出可核查来源；找不到证据时说明不足。
- [ ] 构造有答案、无答案、同词不同义、文档过期四类问题。

验收：比较检索结果是否包含答案，以及最终回答是否忠于证据，不能只评价语言是否流畅。

### E3 显式任务计划（6～10 小时）

书中关联：2.6.2 Agent 状态栏的构成（TODO、目标、约束和进展），另见1.2.4、5.1.3。书中没有单独的“规划章”；以下任务状态设计是工程化练习建议。前置：V4。

- [ ] 每步完成必须有关联工具结果，模型说“完成”不直接代表任务完成。
- [ ] 工具失败后允许修改计划，并限制重新规划次数。
- [ ] 对同一组任务比较直接工具循环与显式计划，观察计划是否增加有效性或只是额外开销。

### E4 基于反馈的反思与经验复用（6～10 小时）

书中关联：9.1 运行轨迹的学习信号、9.2.2 将经验写成指令、9.3。前置：V4、固定评估集。

- [ ] 以真实测试输出或用户纠正作为反馈，生成短的失败原因和下一步修正建议。
- [ ] 将经验与来源任务关联，人工确认后再保存为可复用条目。
- [ ] 限制反思轮数，不能反复自评直到口头宣称成功。
- [ ] 用不同的新任务验证经验是否有效，保留“不反思”的对照。

验收：改进能在结果上观察到，而不只是多了一段分析文字。这里没有训练模型权重。

### E5 双角色协作（10～16 小时）

书中关联：第10章，尤其10.2。前置：V5、明确的成本统计。

- [ ] 从一个执行者、一个只读审查者开始，先串行。
- [ ] 定义传递的任务、证据与结论，避免无上限复制全部对话。
- [ ] 限制往返次数和总预算，执行者统一负责写入，避免两个角色同时改文件。
- [ ] 审查者获得独立检查任务或不同证据，而非仅重复执行者的总结。
- [ ] 与单 Agent 在同一任务集上比较成功率、延迟和费用，收益不足时保留单 Agent。

验收：记录一次审查发现真实缺陷，也记录一次无收益案例；多角色数量本身不是进步指标。

## 下一次练习：V1.3 请求状态与中断恢复

本版边界：仅保存完整成功轮次；请求失败或进程中断时，没有持久化的请求状态。
配置分为 `config.toml`（数据库路径、提示词）与 `llm.toml`（模型连接）；SQL 集中在 `SessionStore`。

按下面顺序推进，每次只完成一小步：

1. **先设计（约一个晚上）**：画出 `pending → succeeded / failed / interrupted` 状态图；设计请求 ID、会话 ID、用户输入、实际模型、时间与错误类别。明确请求记录与有效上下文的区别。
2. **先保存状态**：调用 LLM 前提交 pending；成功时在同一事务内保存完整消息并更新 succeeded；API 失败记录 failed。网络等待期间不持有写事务。
3. **再处理恢复**：单进程启动时，将遗留 pending 标记为 interrupted，不自动重发；提供查看请求记录的入口。回答返回但保存失败时仍展示未保存回复。
4. **最后补观测信息**：记录耗时和服务端实际返回的 token 用量；没有用量时记为空，不编造。不要保存密钥或原始敏感错误响应。

- [ ] 增加数据库结构版本及升级步骤，旧会话内容保留；先练习最小迁移，不引入迁移框架。
- [ ] 成功状态与消息保存原子提交，故障注入后不能出现“状态成功但消息缺失”。
- [ ] 用假模型覆盖成功、API 失败、保存失败；失败输入不混入正常模型历史。
- [ ] 用独立进程模拟请求开始后退出，重启可识别 interrupted，且没有自动网络重试。
- [ ] 亲手演示一次，并解释状态转换和事务边界，再进入 V2 只读工具。

验收目标：能回答“这一轮是否发起、是否完成、为什么失败、重启后如何处理”。
多进程同时使用同一数据库暂不纳入恢复协议，避免误把其他进程的运行中请求标为中断。

提醒：会话持久化是数据保留；上下文构建是决定本次输入；长期记忆是选择可跨任务复用的信息。
