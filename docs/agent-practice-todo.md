### V4.1 可核对的文件修改（未开始）

先支持已有文本文件的单文件精确替换。多文件事务、创建/删除/重命名和通用 patch 解析不纳入这一步。V4.1a/b 先完成本地组件及测试，V4.1c 接齐记录和故障处理后再把编辑能力开放给模型。

#### V4.1a 修改计划与 diff

- [ ] 根据路径、旧文本和新文本生成修改计划，包含原版本标识、候选内容及 diff；规划不修改文件。
- [ ] 旧文本必须恰好匹配一处；未匹配、匹配多处或空匹配均明确失败。
- [ ] 明确支持的编码与文件类型，中文、引号和原有换行形式保持正确，不静默重编码。
- [ ] 验收：正常替换的 diff 准确；失败不产生修改；候选内容与源文件相互独立。

#### V4.1b 确认与可靠写入

- [ ] 展示实际路径及 diff，只执行用户批准的那份计划；拒绝时文件字节不变。
- [ ] 规划和执行都检查写入范围；读取授权不自动等于写入授权。
- [ ] 批准后、写入前再次核对原版本；外部编辑使计划失效，要求重新读取和确认。
- [ ] 采用临时文件和替换方式，避免把目标文件写成半截；说明版本核对与替换不是跨程序事务。
- [ ] 验收：批准、拒绝、越界、外部修改、替换失败以及中文/换行保真；预期失败保留源文件。

#### V4.1c 模型编辑闭环与留痕

- [ ] 将通用编辑工具接入现有工具目录与执行流程，模型收到成功、拒绝、冲突或失败的明确结果；主循环不按工具名称增加分支。
- [ ] 执行记录关联 turn_id、request_id 和 tool_call_id，区分提出计划、获批、实际写入及结果确认。
- [ ] 写入开始记录保存失败时不修改；文件已改但结果日志失败时停止，保留结果未知的诊断信息，不自动重做。
- [ ] 假模型验收“读文件 → 提出替换 → 确认 → 写入 → 回传结果”；拒绝或冲突不得被当成成功。
- [ ] 验收写入后日志失败、进程中断和重启；未知结果不自动重放修改，原日志保留。

- [ ] 自动化先用假模型验证流程；真实模型演示单独记录，不把离线通过等同于模型修复效果已验收。

依据：`tests/features/test_command_execution.py`、[通用命令工具](command-tools.md)。用户已反馈真实模型的成功、拒绝、失败回答；V2.3 固定评估仍按用户决定跳过。各小任务实现时在 `tests/features/` 增补对应业务验收，现在不创建空测试或标记已完成。
